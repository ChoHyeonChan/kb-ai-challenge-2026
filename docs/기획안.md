# 1. 우리가 만드는 것

## 1.0 이름 (확정)

| 구분 | 표기 |
|---|---|
| **서비스명** | **「다 됐나요?」** |
| **과제명** (참가신청서) | **「다 됐나요?」 — 은행 앱이 말해주지 않는 실패 원인 판정 서비스** |
| **팀명** | **다 됐나요** |

**작명 근거** — 사용자가 조치를 하나 끝내고 재시도하며 던지는 질문이 그대로 이름이다.
*"하나 풀었는데 또 있더라"* 는 팀장의 실제 경험(2026-07-26)에서 나왔고,
**앱이 끝내 대답해주지 않는 질문**이라는 점에서 서비스의 존재 이유와 일치한다.

역대 1~7회 입상작 대조: 「KBeep」·「PhiNo」·「cheKB」 등 **영문 조어 다수**, KB 접두어 7건 이상,
순한국어는 「깨비 할머니 통장」·「깨.깨?깨!」 정도. **질문형 이름은 0건**이다.

> ⚠️ **팀명 표기 주의**
> - 공식 FAQ: *"팀명은 참가신청서에 기재된 내용을 기준으로 최종 관리"*
>   → **사이트 회원가입 팀명 = 참가신청서 팀명**이 글자 단위로 같아야 한다.
> - 팀명에는 특수문자(`「」`, `?`)를 넣지 않는다. 폼·파일명·시스템에서 깨질 수 있다.
> - 서비스명(꺾쇠·물음표 포함)은 문서·화면에만 쓴다.

## 1.1 한 줄

> **은행 앱은 "왜 안 되는지"를 말하지 않는다.
> 우리는 흩어진 약관·이용조건을 기계가 판정할 수 있는 규칙으로 바꿔,
> 지금 무엇에 막혔는지 근거와 함께 지목한다.**

## 1.2 ★ 정확한 포지셔닝 — 서비스가 아니라 자산이다

이 제안의 산출물은 **앱 화면이 아니다.** 화면은 자산을 보여주는 창일 뿐이다.

```
진짜 산출물 ①  조건 트리 (Condition Tree)
               = 흩어진 약관·FAQ·이용조건에서 추출한, 판정 가능한 규칙 자산
               → 앱·챗봇·상담원 화면·심사 시스템 어디에나 꽂힌다

진짜 산출물 ②  그 자산을 생산하는 파이프라인
               = 문서를 넣으면 조건 트리가 나오는 자동 변환 엔진
               → 상품이 늘어나도 사람이 규칙을 손으로 안 쓴다
```

> **"이거 KB가 내부에서 만들면 되는 거 아닌가요?"**
> → **네, KB가 만드셔야 합니다.** 저희가 제안하는 건 서비스가 아니라 **방법론과 자산**입니다.
> 조건 트리는 한 번 만들면 앱·챗봇·상담원 화면에 모두 재사용됩니다.

## 1.3 슬로건 (기술설명서에 그대로)

1. **"확인하세요"와 "확인해드렸습니다"의 차이**
2. **"KB는 안내하고 있습니다. 연 2회. 문제는 계좌를 만들려는 그날이 그 2회 중 하루가 아니라는 것입니다."**
3. **"역대 팀들은 약관을 사람에게 쉽게 설명했습니다. 우리는 약관을 기계가 판정할 수 있게 만듭니다."**

## 2.3 문제 정의

> **은행 앱의 실패는 증상만 말하고 원인을 말하지 않는다.**
> 조건은 여러 문서·메뉴·앱에 흩어져 AND로 걸려 있는데, 앱은 "지금 무엇이 안 됐는지"를 알려주지 않는다.
> **정보가 없어서가 아니다. 정보가 필요한 자리에 없어서다.**

## 2.4 왜 아무도 안 고쳤나

1. **앱이 조직도를 반영한다** — 해외결제 설정은 KB Pay에, 계좌는 스타뱅킹에. 고객 목표는 부서를 가로지르는데 이어줄 주체가 없다.
2. **검색은 일반론만 준다** — FAQ는 "확인하세요"라고 말한다. 확인은 사용자 몫이다.
3. **고지 주기와 필요 시점이 어긋난다** — 안심차단은 연 2회 고지. 계좌를 만들려는 날이 그 2회 중 하루일 확률은 극히 낮다.
4. **아무도 측정하지 않았다** — push 지표(발송·오픈·클릭)로 성과를 잰다. pull로 넘어와 실패한 고객은 어느 지표에도 안 잡힌다.

→ 유형: **"아무도 측정을 안 해서"**. 기술 부재도, 수익성 문제도 아니다.

## 2.5 하한선 논증
> **AI를 개발하는 20대 공학도조차 앱 내 검색을 두 번 써야 했고, 결국 포기했다. 이것이 문제의 하한선이다.**
> 조건이 더 나쁜 사용자에게는 더 심각할 것으로 **추정**된다. *(정량 미검증 — 추정으로 명시)*

## 2.6 안심차단의 역설
KB 공식 콘텐츠 제목: *"비대면 계좌개설 **안심차단으로 보이스피싱 피해 예방**하기"*
→ 보호 목적으로 켠 기능이, 그 사람의 비대면 금융을 **전 금융권에서** 막는다. 그리고 그 사실은 연 2회만 고지된다.

## 2.7 고령층은 주제가 아니라 기대효과다

| | 역대 고령층 과제 (2·5·**7회 입상**) | 본 시스템 |
|---|---|---|
| 접근 | **화면을 쉽게 만든다** (종이통장 UI, 목소리 인증) | **왜 안 되는지 알려준다** |
| 대상 | 특정 계층 전용 UI | **연령 무관. 동일 엔진** |

> *"저희는 화면을 쉽게 만들지 않습니다. 왜 안 되는지를 알려줍니다."*
> → 7회 입상작 '깨비 할머니 통장'과 충돌하지 않으면서 접근성 효과를 기대효과로 서술.

# 4. 시스템 설계

## 4.1 파이프라인

```
[오프라인 — 자산 구축]                          담당: 현찬
  KB 공개문서 수집 (약관·이용조건·FAQ·안내)
        ↓  atomic snippet 분할
        ↓  ★ LLM 조건 추출 (directed symbolic prompting)
        ↓  스키마 강제 출력 + evidence 스팬 링크 + confidence
   조건 트리 JSON  ─────────────┐   ← ★ 이것이 재사용 가능한 자산
                                │      인터페이스 계약 C1
[온라인 — 판정]                  │
  "해외결제가 안 돼요"            │
        ↓  목표 선택              │   ▣ 예선: 목표를 직접 고른다(드롭다운)
        ↓  목표 → 조건트리 ───────┘   ▢ 계획: 자연어 질의 → goal_id (LLM+RAG)
        ↓
   ◆ 규칙 엔진: 사용자상태 × 조건트리 → 충족/미충족/불명       ▣ 구현됨
        ↓  [결정론적. 같은 입력 = 같은 출력 — 2,000회 100% 실측]
        ↓
   ◆ 해결 계획: "하나만 풀면 어떻게 되나"                     ▣ 구현됨 (LLM 미사용)
        ↓
   화면: ✕ 미충족 + 근거 원문 + 다음 행동 + 조건트리 원본     ▣ 구현됨
```

> **▣ 구현됨 / ▢ 개발 계획** — 예선 제출본의 범위를 그림에 그대로 표시한다.
> 자연어 목표 식별(▢)은 8장 개발 계획 1단계다. **지금은 목표를 직접 고르는 방식으로 동작한다.**
> 미충족 사유를 LLM 이 문장으로 설명하는 단계는 **의도적으로 넣지 않았다** — 근거 원문을
> 그대로 보여주는 편이 "원문 밖 생성 0건"을 구조적으로 보장한다 (12장 참조).

## 4.2 AI / 규칙 분담 — ★ 기술 적정성의 핵심

| 단계 | 담당 | 근거 |
|---|---|---|
| 조건 문장 식별·구조화 | **LLM + 스키마 강제** | 비정형 자연어, 예외구조("다만 ~인 경우 제외") |
| 문서 간 조건 병합 | 규칙 (문서 간 합의) | ▣ 구현됨. 임베딩 없이 label 유사도 + 합의로 대표 선정 |
| 조건 검수 | **사람** | ▣ 구현됨. 승인/반려만. 조건을 쓰지는 않는다 |
| 질의 → 목표 식별 | **LLM** | ▢ 개발 계획. 예선은 목표 직접 선택 |
| 목표 → 조건트리 검색 | **RAG** | ▢ 개발 계획 (목표가 2종이라 지금은 직접 조회) |
| **충족/미충족 판정** | **규칙 엔진(코드)** | ▣ ★ 실행 시점 LLM 판단 금지. 2,000회 100% 일치 실측 |
| 해결 계획 ("하나만 풀면?") | 규칙 (집합 연산) | ▣ 구현됨. LLM 미사용 |
| 미충족 사유 설명 | — | ▢ **넣지 않았다.** 근거 원문을 그대로 노출하는 편이 안전하다 |

> **판정은 절대 LLM이 하지 않는다.** 동일 입력 N회 반복 일치율을 측정해 증거로 제출한다.

## 4.3 기술 신규성 — 일반 RAG와의 차이

```
일반 RAG:  질의 → 문서 검색 → 답변 생성          (생성이 종착점)
우리:      질의 → 조건 검색 → 판정 실행 → 근거     (실행이 종착점)
```
검색 결과가 텍스트로 소비되지 않고 **실행 가능한 술어(predicate)로 소비**된다.
→ Retrieval-Augmented **Generation**이 아니라 Retrieval-Augmented **Verification**.

## 4.4 ★ 실제와 가상의 경계 (데모에 명시)

의심받을 것을 먼저 밝힌다. 데모 화면 상단에 배지로 표시한다.

| 구분 | 내용 | 상태 |
|---|---|---|
| **실제** | 조건 트리 — **KB 공개문서에서 자동 추출** (수집일 명시) | ✅ 진짜 |
| **실제** | 판정 엔진 — 결정론적 규칙 평가 | ✅ 진짜 |
| **실제** | 근거 원문 — 수집한 문서의 실제 문장 | ✅ 진짜 |
| **가상** | 사용자 상태 — 데모 프로필 | ⚠️ 실 연동엔 내부 API 필요 |

> **이 시스템에서 "가짜"는 사용자 상태 하나뿐이다.** 나머지는 전부 실제 문서에서 나온다.

# 5. 데모 시나리오 2종 — 하나의 엔진, 두 케이스

> 순서에 의도가 있다. **흔한 문제로 규모를 세우고, 극단적 사례로 임팩트를 찍는다.**

## 5.1 시나리오 ① 해외결제 — *흔한 문제*

**대상 규모**: 해외직구·해외 구독 서비스(AI 도구 포함) 이용자 전반

> 아래는 **실제 산출물이다.** 조건 11개는 KB 공개문서에서 자동 추출해 검수를 통과한 것이고,
> 판정·계획은 규칙 엔진이 계산한 값이다. (`data/trees/overseas_payment_online.json`)

```
사용자: "해외 결제가 안 돼요"

  판정 — 조건 11개 중  미충족 3 · 확인불가 1

  ✕ 해외원화결제(DCC) 차단 해제   → 앱에서 가능: KB Pay            [근거 3곳 ▾]
  ✕ 해외거래정지 해제             → 앱에서 가능: 같은 화면 별도 항목 [근거 4곳 ▾]
  ✕ IC칩 비밀번호 등록            → 앱에서 불가: 영업점 또는 ATM    [근거 5곳 ▾]
  ✓ 카드 잠김 없음 · 명의도용 차단 해제 · 뒷면 서명
  ✓ 1일 / 1회 / T&E 누적 한도 · 카드 유효기한
  ? 카드–여권 영문명 일치         (여권 정보 미보유)

  ── 하나만 풀면 되나요? ──────────────────────────
  DCC 차단만 해제        → 여전히 안 됩니다 · 필수 조건 2개 남음
  해외거래정지만 해제     → 여전히 안 됩니다 · 필수 조건 2개 남음
  앱에서 할 수 있는 것 모두 → 여전히 안 됩니다 · 필수 조건 1개 남음
  3개 모두               → 됩니다

  ⚠ 3개를 모두 해결해야 합니다. 그중 1개는 앱에서 할 수 없어
    그것이 전체 소요를 결정합니다 — 먼저 시작하세요.
```
- **설정 화면에 보이는 2개 + 보이지 않는 9개**를 한 자리에서 판정
- 마지막 두 블록이 핵심 — **앱이 결코 해주지 않는 말**
  ("하나 풀어도 안 됩니다" / "이건 앱에서 못 풉니다")
- `?`(확인 불가)를 **일부러 화면에 노출**한다. 전부 ✓/✕로만 채우면 그게 오히려 거짓말이다
- 이 계획 계산에도 **LLM을 쓰지 않는다.** 판정 결과를 집합 연산으로 다시 평가할 뿐이며,
  없는 사용자 값을 지어내지 않는다 (`src/judge/simulate.py`)

## 5.2 시나리오 ② 비대면 계좌개설 — *극단적 사례*

> 아래는 **실제 산출물이다** (`data/trees/account_open_nonface.json`).

```
앱:  "신분증이 인식되지 않습니다. 다시 촬영해 주세요."
     └ 사용자는 재촬영을 반복하다 포기한다

우리: 계좌개설 가능 조건 판정 — 조건 1개 중 미충족 1

  ✕ 비대면 계좌개설 안심차단이 해제되어 있어야 합니다
       · 앱에서 해결 불가 — 영업점 방문 (신분증 지참)
       · 근거 5곳 · 문서 2종 (KB 보안센터 공식 안내 포함)
       [근거] "비대면 계좌개설 안심차단 서비스를 신청한 후에 모바일 앱이나
               인터넷뱅킹에서 새로운 계좌를 만들려면 서비스를 해제해야 하는데요.
               서비스 해제는 반드시 지점을 방문해 직접 신청해야 합니다." ▾

  → "다시 촬영해도, 다른 은행에 가도 개설되지 않습니다."
```

### ⚠️ 이 시나리오의 조건은 1개다 — 왜 그런지 밝힌다

기획 단계에서는 신분증 품질·휴대폰 인증·최근 개설 이력까지 **여러 조건을 예상했다.**
그러나 KB 공개문서를 실제로 추출해 보니, **판정 가능한 조건은 안심차단 하나뿐이었다.**
나머지는 공개문서에 판정 기준이 없다 — 예상했다는 이유로 조건을 지어내지 않았다.

> **이것이 오히려 이 시나리오의 논점이다.**
> 조건이 하나뿐인데도 사용자는 그 하나를 모른다. 앱은 "다시 촬영하라"고만 말한다.
> 조건의 개수가 아니라 **앱에서 풀 수 없다는 사실**이 이 사례의 임팩트다.

## 5.3 두 시나리오의 대칭

| | ① 해외결제 | ② 계좌개설 |
|---|---|---|
| 역할 | **규모** — 흔한 문제 | **임팩트** — 극단적 사례 |
| 앱이 하는 말 | (결제 실패, 원인 미고지) | "다시 촬영해 주세요" |
| 사용자 행동 | 하나 해제 → 재시도 → 실패 → 재탐색 | 재촬영 반복 → 포기 |
| 자동 추출된 조건 수 | **11개** (화면엔 2개) | **1개** (그 하나를 모른다) |
| 앱에서 해결 불가 | 8 / 11 | 1 / 1 |
| 실제 구조 | **셋을 모두 해제해야 함** | 아무리 찍어도 안 됨. **영업점 방문 필요** |
| 근거 | KB Pay 실측 + 공식 FAQ (문서 6종) | KB 보안센터 공식 원문 (문서 2종·근거 5곳) |
| 증언 | 현찬 본인 | 현찬 본인 |

→ 둘 다 **"시도한 해결책이 구조적으로 통하지 않는 상황"**.

## 6.3 ★ 신규성 위치 — 가장 가까운 선행연구와의 차이

> **"아무도 안 했다"고 주장하지 않는다.** 가장 가까운 연구를 먼저 제시하고, 무엇이 다른지 밝힌다.

**가장 가까운 선행연구 2편**
- **공공 자격심사** (FAccT 2026): 규정 → 자격요건 온톨로지 → **기관 결정의 설명이 법에 맞는지 검증**
- **통신 소비자보호규약** (2506.08899): 소비자보호 규약 → deontic 규칙 **형식화**

**본 연구와 다른 네 가지**

| 축 | 선행연구 | 본 연구 |
|---|---|---|
| ① 문서 | 법령·공공규정 (단일 권위 문서) | **상업 약관·이용조건·FAQ** — 조건이 여러 문서·여러 앱에 흩어져 있음 |
| ② 사용자 | 기관·감사자·정책 담당 | **개인 소비자 본인** |
| ③ 목적 | 결정의 정당성 **사후 검증** | 실행 실패의 **사전 진단** |
| ④ 출력 | 준수/위반 판정 | 미충족 항목 + **해결 경로**(앱 내 조치 가능 여부 포함) |

> **핵심 차이는 ①과 ④다.** 법령은 한 문서에 모여 있지만 **약관·이용조건은 흩어져 있고**, 그래서 "조건을 모으는 것" 자체가 과제가 된다. 그리고 우리는 판정에서 멈추지 않고 **"그래서 지금 어디로 가야 하는가"** 까지 출력한다.

> 온라인 결제 목표에서는 "결제 시점 유효"로 해석해 옮긴 것이다. **해석이 개입한 조건은 신뢰도를 낮춰 표시한다.**

### op 세트 (팀원이 구현할 전부)

| 분류 | op | 비고 |
|---|---|---|
| 동등 | `eq` `neq` `in` `not_in` | |
| 수치 | `gte` `lte` `gt` `lt` | |
| 존재 | `exists` `not_exists` | |
| **시간** | `date_after` `date_before` | value에 날짜 또는 `{"ref": ...}` |
| **시간** | `within_days` `not_within_days` | `{"days": 20}` — 기준일로부터 |
| **횟수** | `count_lte` `count_gte` | `{"days": 20, "n": 0}` — 기간 내 횟수 |

### value 표현
- 리터럴: `false`, `6000000`, `"2027-05"`
- 참조: `{ "ref": "context.travel_end_date" }`
- 상대시간: `{ "now_plus_days": 7 }`

### 설계 의도 (★ 이게 우리 철학을 데이터에 박아넣는 부분)

| 필드 | 의도 |
|---|---|
| **`evidence` 필수** | 근거 없는 조건은 트리에 들어갈 수 없다 → **근거 표시율 100%가 구조적으로 보장** |
| **`evidence.confidence`** | 추출 신뢰도. `low`면 화면에서 "검토 필요"로 표시 → **모르는 걸 아는 척하지 않음** |
| **`remedy.actionable_in_app`** | **앱에서 못 고치는 것**을 데이터로 구분. 안심차단이 `false` — 우리 핵심 인사이트를 스키마에 박음 |
| **`category`** | setting / document / limit / temporal / eligibility — 화면 그룹핑 + 추출 프롬프트 가이드 |
| `predicate` | **LLM이 만들고 규칙 엔진이 평가한다.** LLM은 평가에 관여하지 않음 |
| `severity` | blocking(막힘) / warning(주의) |

# 12. 한계 (먼저 쓴다)

1. 실제 앱 상태 조회 불가 → **가상 프로필로 판정 로직 실증** (조건 추출·근거는 실제)
2. 수집 범위 2개 도메인 (전 상품 커버 아님)
3. 약관 오픈 API 부재 → 수집 의존, 개정 감지 수동 트리거
4. 조건 추출 정확도는 소규모 수동 라벨 기준 (대규모 벤치마크 아님)
5. 딥링크 실제 연결 불가 → 경로 안내 화면으로 대체
6. **안심차단 상태에서 앱이 표시하는 실제 문구 미확인** (검증 목적 활성화 불가 — 해제에 영업점 방문 필요)
7. **문제 발생 빈도의 정량 통계 없음** — 안심차단 가입자 수 등 미공개. 그래서 특정 원인이 아니라 **"원인이 흩어져 있다는 구조"** 를 문제로 정의함
8. 고령층 관련 서술은 **추정**
9. **예선 제출 범위**: 목표를 자연어로 알아듣는 단계(LLM 목표 식별)는 넣지 않았다.
   목표가 2종이라 직접 선택으로 충분했고, LLM 을 데모 경로에 넣으면 실패 처리가 따라붙는다.
   → 15장 개발 계획 1단계. **지금 되는 것과 앞으로 할 것을 그림에서 구분해 표시했다** (4.1)
10. **미충족 사유를 문장으로 생성하지 않는다.** 근거 원문을 그대로 보여준다.
    설명을 생성하면 원문 밖 문장이 나올 위험이 생긴다 — 그 위험을 아예 만들지 않는 쪽을 택했다

| 경계 | **"이 문제 겪는 사람이 몇 명인가요?"** | 특정 원인의 빈도 통계는 공개돼 있지 않습니다. 그래서 저희는 **한 가지 원인이 아니라 "원인이 흩어져 있다는 구조"** 를 문제로 잡았습니다. 해외결제는 저희가 KB 공개문서에서 자동 추출한 조건만 11개인데 화면엔 2개만 보입니다 — 이건 빈도와 무관한 구조 문제입니다. |
| 차별화 | "저희 AI 상담 챗봇이 이미 안내하는데요?" | 챗봇은 **방법**을 답합니다. 저희는 **상태**를 판정합니다. 챗봇은 고객이 무엇을 켜뒀는지 모르므로 "이제 다 됐나요?"에 답할 수 없습니다. |
| 차별화 | "1회 약관 분류기, 6회 KB:OT와 뭐가 다르죠?" | 그 팀들은 약관을 **사람에게 설명**했습니다. 저희는 약관을 **기계가 판정할 수 있는 규칙**으로 바꿉니다. 출력이 문장이 아니라 참/거짓과 근거 조항입니다. |
| 차별화 | "4회 비대면 본인확인 팀과 겹치지 않나요?" | 그 팀은 신분증 **이미지**를 다뤘습니다. 저희는 이미지를 건드리지 않습니다. **촬영이 문제가 아니었던 경우**를 찾는 게 저희 영역입니다. |
| 경계 | "앱 전체 메뉴를 커버하나요?" | 아니요. 2개 목표만 실증했습니다. 약관 문서만 추가하면 확장되는 구조입니다. **커버리지를 과장하지 않는 것이 설계 원칙**입니다. |
| 약점 | "실제 앱 상태를 어떻게 읽죠?" | 못 읽습니다. 내부 API 연동이 전제입니다. **가상 프로필로 판정 로직을 실증**했고, 조건 추출과 근거는 실제 문서입니다. |
| 약점 | "LLM이 조건을 잘못 뽑으면요?" | 그래서 **판정은 LLM이 하지 않습니다.** 추출 조건에 근거 원문이 붙어 사람이 검증할 수 있고, 신뢰도가 낮으면 `low_confidence`로 분리 표시합니다. 판정은 결정론적 엔진이 하며 동일 입력 N회 일치율을 측정해 제출합니다. |
| 약점 | "약관이 개정되면요?" | 조건마다 수집 일시를 기록합니다. 재수집이 자동이라 재실행하면 갱신됩니다. 다만 **개정 감지는 현재 수동 트리거**이며 한계에 적었습니다. |
